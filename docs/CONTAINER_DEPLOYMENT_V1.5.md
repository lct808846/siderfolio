# AstroAgent V1.5 项目整体容器化部署方案

**状态：V1.5.0改动范围的本机自动验收通过；发布与远程CI以实际版本状态为准。** 具体测试、首次失败、资源与限制见[最终记录](test-records/v1.5.0/remaining/20261113T003239Z/README.md)。 本文是 [V1.5 开发文档](PROJECT_PLAN_V1.5.md)的一部分；实际文件、Docker Desktop 执行边界、离线导入和未执行边界见[容器实施记录](development/v1.5.0/CONTAINER_IMPLEMENTATION.md)。先以 Windows + Docker Desktop（Linux amd64容器）个人本机部署为目标，Linux主机为兼容目标；不等同于公网多用户或企业生产环境部署。

## 1. 交付目标与拓扑

在准备好 Docker、配置、模型与数据目录后，通过项目提供的 Compose 配置管理整个系统，而不仅仅容器化小模型。正常使用路径包括网页、会话和历史、SIMBAD/ADS/Gaia、知识库与 RAG、本地模型命名和文本操作，以及 Python/Gnuplot 绘图的审阅、隔离执行、预览和选择保存。外部科研服务和远程回答模型仍需网络及用户自行配置的凭据。

```text
浏览器（本机） → ingress → frontend → backend ─┬→ postgres（pgvector + pg_trgm）
                                     ├→ ollama（Qwen 本地推理）
                                     ├→ 只读嵌入模型文件（RAG）
                                     ├→ plot-executor → 隔离绘图任务
                                     └→ 外部科研服务 / 用户配置的远程模型
```

| 组件 | 计划职责与连接 | 数据与暴露 |
| --- | --- | --- |
| `ingress` | 仅负责本机流量转发 | 仅 `127.0.0.1:5173` 发布网页端口，不持有密钥或 Docker Socket |
| `frontend` | 构建 Vue 静态文件并提供同源 API 代理 | 仅连接内部网络，不直接发布宿主端口 |
| `backend` | FastAPI、Agent、知识库、模型适配与绘图任务协调 | 不发布宿主端口；连接内部服务；读取服务端密钥及只读嵌入模型 |
| `postgres` | PostgreSQL，具备与项目兼容的 pgvector 和 pg_trgm | 数据存储在独立命名卷；不发布数据库端口；版本和镜像摘要经兼容性确认后固定 |
| `ollama` | 本地 Qwen 生成推理 | 模型存储持久化；不发布宿主端口；本地模型是可选能力，缺失时按原有规则降级 |
| `plot-executor` | 独立绘图任务调度边界 | 不发布宿主端口；管理受限临时绘图容器；任务文件与数据库、模型、密钥隔离 |

前端可采用现有 Node 静态服务器或经验证的反向代理；须维持同源 API 与安全响应头。后端允许访问外部科研服务，内部网络划分应支持所需出口，并限制服务间访问；Compose 网络本身不能代替应用授权或完整出站防火墙。

## 2. 部署交付物与启动

实现时提供前后端镜像构建文件、Compose 配置、`.dockerignore`、不含真实密钥的配置示例和操作手册；锁定基础镜像、依赖及绘图镜像版本/摘要并记录来源。构建上下文排除 `.git`、`.env`、密钥、数据库备份、模型权重、用户文档、生成产物、`node_modules` 等，不将个人数据打包进镜像。

首次准备顺序：核对磁盘、内存与 Docker 环境；复制配置模板到未纳入版本控制的本地配置文件并设置数据库凭据、模型与嵌入模型路径；构建镜像并启动；用户在设置页核对并明确初始化独立空库；按第 4 节明确导入模型。目标启动入口为 `docker compose up -d --build`，但这条命令本身不完成模型导入、数据库确认或绘图安全准备；具体文件和操作完成后才可使用。停止服务不得删除持久卷；删除卷或重建数据库必须单独明确操作，文档不得将其作为常规排错步骤。

数据库健康检查可作为后端启动依赖；前端与后端应显示服务启动和故障状态，数据库重启后应可重连。Compose 的运行顺序不等于服务已就绪，需要健康检查和应用端故障处理，参见 [Docker Compose 启动顺序文档](https://docs.docker.com/compose/how-tos/startup-order/)。Ollama 未就绪不能阻止查看历史或使用不依赖它的功能；缺少绘图执行器时绘图明确不可用。

## 3. 网络、配置与安全

- 浏览器只访问本机前端；数据库、Ollama、后端及执行器不对局域网或公网发布。前端转发至固定的 `backend:8000`，后端访问固定的 `ollama:11434`，具体协议及端口由实现固定并写入配置模板。
- 每个容器的 `127.0.0.1` 都指向自身。当前前端 `frontend/server.mjs` 限定后端为回环地址且仅监听回环；本地模型客户端及 Host/Origin 防护也以本机为前提。实现需显式引入容器部署模式和服务端固定目标白名单，同时保留原生模式现有回环限制；拒绝前端传入任意地址、重定向、凭据 URL 和非预期目的地。不可为了跨容器访问而全局放宽目标地址或 Host/Origin。
- 代理明确传递受信任的 Host/Origin，后端只接受预设的本机网页来源；检查跨站请求、伪造 Host、代理路径及绕过代理的访问。容器内部监听地址不是对公网开放的授权。
- 数据库凭据、远程模型密钥与 ADS token 仅供服务端使用；不写入前端构建变量、镜像层、仓库、日志或验收截图。本地配置限制文件权限，日志和错误信息脱敏。生产部署所需的身份认证、TLS 和访问控制另行设计，不将本方案直接暴露公网。
- 前后端及执行器尽可能采用非特权用户、只读根文件系统、最小权限和资源限制；明确必要的临时可写目录。限制日志大小，避免模型或绘图任务耗尽磁盘、内存与 CPU。

## 4. 数据、模型和迁移

**数据库：** 首次创建独立 PostgreSQL 数据卷及专用账户，安装兼容的 pgvector 和 pg_trgm；由用户核对后显式初始化，绝不启动时自动清库、覆盖或向现有数据库写入。数据库角色与扩展创建权限要与首次设置流程相符，日常应用尽可能使用较低权限。保留现有 PostgreSQL + pgvector 架构，不引入 SQLite。

**持久化与恢复：** 保存数据库卷、用户选择持久保存的绘图产物和必要配置；明确数据库记录与图像文件的对应关系。提供一致性数据库备份及产物、配置的备份/恢复步骤，记录版本和完整性校验；备份不包含模型权重及密钥，密钥另行安全保存。升级前备份，迁移由单一受控执行者显式执行，失败保留原数据并说明回退及不可逆边界；恢复先在独立空环境演练，不直接覆盖日常库。

**已有数据：** 默认使用新卷，与用户当前宿主 PostgreSQL 完全分开，不自动连接、迁移或复制。需要迁移时先核对来源、目标、版本和备份，由用户明确发起导出及导入；验证会话、文献、索引和绘图产物后再决定是否切换，保留原数据。绝不将新卷初始化误认为已迁移旧数据。

**RAG 嵌入模型：** 已准备的本地嵌入模型与 Qwen 是独立模型。由用户配置宿主路径，以只读方式挂载到后端固定容器路径；核对路径映射、模型身份/哈希与现有索引对应关系，不随镜像复制或自动下载。模型缺失或不匹配时显示明确原因，按现有规则使用可用功能，不能声称语义检索已就绪。

**Qwen 与 Ollama：** 容器化 Ollama 使用独立持久卷；宿主机现有 Ollama 已注册模型不会自动出现在新卷中。提供明确的离线导入/注册步骤：用户选择现有 GGUF 及模板，核对来源、标签、量化和摘要后导入，并验证容器中实际注册身份；不得自动下载或覆盖原模型。也可另行设计受控连接宿主服务的模式，但须明确地址、安全边界和跨平台差异，不作为容器模型已就绪的证据。CPU 为基础路径；GPU 加速为可选配置，需检查设备、驱动、Docker GPU 支持及 Ollama 兼容性，性能和内存以实测为准。

## 5. 绘图执行隔离

现有绘图实现通过 Docker CLI 创建 Linux 隔离任务。后端自身容器不能直接依赖宿主回环、任意主机路径或将 Docker socket 挂入 Web 后端。新增专用 `plot-executor`，由后端通过内部固定接口提交经过审阅的 Python/Gnuplot 任务；执行器使用独立认证凭据、固定操作类型与协议，校验任务 ID、尺寸、输入、产物路径及请求来源，不接受任意镜像、挂载、命令行、Docker 参数或主机路径。

按用户决定使用 Docker Desktop + WSL2，不创建 VMware 虚拟机。`plot-executor` 是不发布端口的受信任内部服务，独占访问 Docker Desktop Socket；Web 后端、前端和绘图任务均不挂载 Socket。它只暴露认证后的固定绘图操作，不接收任意镜像、挂载或 Docker 参数。**残余风险：** Socket 的只读挂载不限制 API 写操作；若执行器被攻破，攻击者可能控制同一 Docker 守护进程、其他容器与卷及允许挂载的宿主文件。该风险高于独立守护进程，内部网络和认证不能消除它；不得用于不受信任的公网多租户。详见 [Docker daemon 访问保护](https://docs.docker.com/engine/security/protect-access/)。

每个任务仅使用固定摘要的协议 2 绘图镜像，保持既有隔离要求：禁止网络、非特权、只读根文件系统、能力集与系统调用限制、CPU/内存/进程数/执行时长和输出大小上限；输入只读，输出写入专用临时目录并经过路径、类型、大小校验后交回后端。完成、失败或超时均清理临时资源，避免符号链接和路径穿越；任务不接触数据库凭据、模型文件或宿主用户目录。需针对 Docker daemon 所在环境设计共享目录或安全传输，不能假定容器路径就是宿主路径。

执行器或隔离条件不满足时关闭绘图执行并告知原因，不回退宿主直接运行，也不削弱隔离来凑齐功能；在 Python 和 Gnuplot 两条端到端路径均通过之前，不能把整体容器化标为完整通过。

## 6. 实施与验收

1. **基线与配置：** 清点原生运行、依赖、端口、数据及现有模型；选择并固定兼容的镜像版本，确定 Windows/Linux 的路径和卷策略。
2. **核心服务：** 编写前后端镜像及 Compose，适配固定内部服务地址和安全校验，接入 PostgreSQL、健康检查、配置与可恢复故障提示。
3. **模型与数据：** 接入只读嵌入模型和 Ollama 持久卷；编写离线模型导入、数据库初始化、备份恢复及已有数据迁移手册。
4. **安全绘图：** 实现独立执行协议、受限执行环境、输入输出管理与清理，保留原有审阅、预览、下载和保存流程。
5. **用户安排验收：** 在隔离环境执行以下检查并记录提交、镜像摘要、配置、系统、失败和限制；不把既有原生部署验收当作容器验收。

待验收项目：

- [ ] 从干净环境按文档部署；仅网页绑定本机，健康状态、启动顺序和故障提示正确，重启后服务恢复。
- [ ] 用户确认后初始化独立 PostgreSQL，重启和镜像更新后会话、知识库与保存的产物仍在；备份恢复、迁移和失败回退在隔离环境验证，既有数据库不受影响。
- [ ] 嵌入模型身份与索引一致；完成文献导入、索引、检索预览、用户确认和引用问答，模型缺失及数据库不可用时状态明确。
- [ ] 容器内 Qwen 身份与预期一致，自动命名、手动优先和轻量文本任务可用；关闭或故障时原有聊天继续，且不发生隐式远程回退。
- [ ] 会话历史、模型服务和 SIMBAD/ADS/Gaia 查询按实际凭据与网络条件验证；对外部服务失败保留真实结果和原因。
- [ ] Python 和 Gnuplot 均能审阅、隔离执行、网页预览和由用户选择保存；验证超时、资源限制、路径穿越、网络隔离、执行器不可用及清理。
- [ ] 验证服务地址白名单、Host/Origin、防止密钥泄漏、无宿主 Docker socket 暴露给后端与任务；记录执行器特权及隔离边界。
- [ ] 记录 CPU/GPU、内存、磁盘占用与启动/推理表现；GPU 不可用时 CPU 路径和资源不足提示符合实际。完成数据库恢复演练，文档与实际文件一致。

开发期间遵循项目约定，不主动启动容器、运行测试或操作个人数据库；由用户安排发布前验收。仅构建成功、容器运行或模型已下载都不构成项目完整交付的证据。
