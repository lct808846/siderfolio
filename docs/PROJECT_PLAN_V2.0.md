# Siderfolio V2.0 开发文档｜正式部署与多人使用

**日期** 2026-11-23　**目标版本** `2.0.0`　**状态** 已完成联合验收并发布源码（公网服务器上线待目标实例配置后执行）

V2.0 的目标是交付一套可由个人或小课题组独立部署、长期使用并在故障后恢复的天文科研工作台。范围包括服务器部署、多人隔离与配额、后台任务可靠性、备份恢复及版本验收。本版采用 Siderfolio 作为产品名称。

实施基线为正式源码版本 `v1.9.0`，包含个人文献库、运行追踪和固定评估框架。V2.0 实施及验收分别记录采用的实际代码提交、配置与镜像。[V1.9 发布说明](development/v1.9.0/RELEASE.md) · [V1.9 实施说明](development/v1.9.0/IMPLEMENTATION.md)

## 1. 服务器部署与升级

V2.0 的首个生产目标是把 Siderfolio 部署到 GCP 单台 Linux 虚拟机。GCP 配置草案已完成 Compose 配置解析和脚本语法检查。V2.0 开发时再完成配置定版与构建，按当前安排先在目标服务器启动公网入口，功能和恢复演练另行验收。[GCP 部署配置](../containers/gcp/README.md) · [现有容器部署方案](CONTAINER_DEPLOYMENT_V1.5.md)

本机默认在 5173 使用独立开发数据库预览，Vue 与 FastAPI 优先热更新，依赖或构建配置变化时只重建受影响的开发服务。GCP 公网实例用于正式日常使用。签名版本发布工作流覆盖 CI、GHCR 与受限 GCP 更新，见[开发与发布手册](DEVELOPMENT_AND_RELEASE.md)。

### 1.1 目标环境与公网入口

| 项目 | 已知条件与部署要求 |
| --- | --- |
| 服务器 | Google Compute Engine 新加坡区 `asia-southeast1`，`n2-standard-2`（2 vCPU、8 GiB RAM），80 GB 平衡永久性 SSD，Ubuntu 24.04 LTS x86_64 |
| 已有工具 | Docker、Docker Compose v2、Git。实施时核对构建工具与端口占用 |
| 网络 | 已在 GCP 防火墙放行 TCP 80／443。上线前确认规则应用到目标实例。Gemini 和海外学术／天文接口走直接出站连接，无需 HTTP 或 SOCKS 代理 |
| 域名模式 | 将 DNS 解析到目标实例，在 `SITE_MODE=domain` 下由 Caddy 接入 80／443，自动签发与续期可信 HTTPS 证书 |
| 公网 IPv4 模式 | 暂无域名时使用稳定公网 IPv4，设置 `SITE_MODE=ip`，Caddy 在 80 端口接受 IP 访问并跳转至同一 IP 的 HTTPS。实施时核对 IP 证书签发、续期和公网访问 |

浏览器经 Caddy 访问 Vue 网页，网页和 FastAPI 接口使用同一站点地址。只由 Caddy 发布公网端口，FastAPI、PostgreSQL + pgvector、执行器及健康探针留在 Docker 网络内。登录、邮件激活和密码找回使用同一个可信 HTTPS 地址，保持 Cookie、Host／Origin 和 CSRF 校验。证书状态保存在持久卷中。[身份与部署说明](development/v1.6.0/OPERATIONS.md)

### 1.2 配置交付与默认启用范围

| 交付 | V2.0 要求 |
| --- | --- |
| 镜像 | 沿用项目的 Vue 和 FastAPI 构建，补齐 Caddy 与 PostgreSQL 初始化镜像，锁定正式交付的镜像、依赖与源码版本。[GCP Dockerfile](../containers/gcp/Dockerfile) |
| 编排与代理 | 配齐生产 `docker-compose.yml`、Caddy 反向代理、持久卷和健康检查。所有常驻容器设置 `restart: unless-stopped`，`json-file` 日志每个文件 `max-size: "50m"`，最多 3 个。[Compose 配置](../containers/gcp/docker-compose.yml) · [Caddyfile](../containers/gcp/Caddyfile) |
| 私有配置 | 发布无真实凭据的 `.env.example`。通过服务器上的 `containers/gcp/.env`（权限 `0600`）注入变量，`.gitignore` 和构建上下文均排除该文件。Gemini、邮件与 ADS 凭据仅注入后端，数据库管理与应用角色使用各自的密码。前端和镜像均排除密钥。[环境变量模板](../containers/gcp/.env.example) |
| 脚本与手册 | 提供从克隆、配置、串行构建、启动到验证的命令，以及更新、回退和备份说明。更新保留原有私有配置和数据卷，先核对数据库兼容性并备份。[部署脚本](../containers/gcp/deploy.sh) · [部署手册](../containers/gcp/README.md) |

默认启动 Caddy、前端、后端和数据库，聊天使用 Gemini，保留已配置的天文查询和基础知识库检索。基于 2 vCPU／8 GiB 的规格，首装串行构建。Ollama、N 体 Worker、语义 RAG 和脚本绘图按需启用，分别明确资源预算及启用条件。语义检索使用校验过的本地嵌入模型，绘图使用专用隔离执行器，公网后端保持与 Docker 控制接口隔离。[可选功能的当前配置](../containers/gcp/README.md#4-单机资源与功能开关)

### 1.3 从克隆到启动验证

以下为 V2.0 发布时的 SSH 命令草案，以实际批准发布的源码和最终脚本为准。示例用发布标签 `v2.0.0`。数据库初始化、迁移和恢复按项目约定单独授权。只有确认是全新空库并获准初始化时才使用 `--init-db`。

```bash
set -e
git clone --depth 1 --branch v2.0.0 https://github.com/lct808846/astroagent.git astroagent-v2
cd astroagent-v2
bash containers/gcp/deploy.sh prepare
vi containers/gcp/.env
bash containers/gcp/deploy.sh deploy --init-db
bash containers/gcp/deploy.sh verify
```

已有部署按升级手册检出目标版本，备份并确认兼容后使用 `deploy` 更新。启动检查核对 HTTP 跳转 `308`、有效 HTTPS 证书、登录页和认证接口 `200`、匿名业务请求 `401`、公网内部探针 `404`，并区分关键依赖与可选功能的就绪状态。探针不发起付费模型调用。

发布验收另从外网核对 DNS 或公网 IP、登录和证书，实际收到激活及密码重置邮件后完成对应流程，验证首位管理员 MFA 和手动访问 `/admin`，并按启用范围核对 Gemini、ADS、SIMBAD、Gaia 和可选运行环境。记录实际部署提交、镜像、配置和结果。[首位管理员操作流程](development/v1.6.0/OPERATIONS.md#3-初始化首位管理员)

### 1.4 实施时补齐的信息

当前资料足够完成 V2.0 规划。部署前再确认以下信息。

- **访问地址。** 已解析的域名，或目标实例的稳定公网 IPv4。可按需设置证书联系邮箱。
- **模型和发件。** 确认 Google 项目启用的 Gemini 模型，以及发件服务的地址、端口、加密方式和发件地址。Gemini API Key、SMTP 登录凭据和可选的 ADS Token 直接填入服务器私有 `.env`。数据库密码及内部密钥由脚本在服务器生成。
- **数据及启用范围。** 确认全新部署或迁移已有账号、会话、文献及其他数据。需迁移时明确来源实例和范围，同时确定是否首批启用 N 体计算、语义 RAG 和脚本绘图。

## 2. 多人使用、配额与运维

- **账号与数据。** 复用邮箱激活、登录、管理员 MFA 和 PostgreSQL 账号隔离。部署者可控制注册是否开放，首轮部署面向受控的小范围用户。站点业务继续要求登录，后台保持手动访问地址。会话、项目、个人文献库、RAG、附件、下载和运行详情在服务端按账号校验权限，管理员查看必要的状态和汇总用量。
- **配额与并发。** 管理员可配置每账号的模型请求、ADS 等查询频率、存储、任务排队数量和运行并发。系统同时设置全局容量与上游配额，给网页和登录保留响应能力。高成本请求在发模型或进队列前校验并占用额度，完成、失败、取消后按契约结算。幂等重试复用原操作记录。未上报用量显示未知，费用估算保留价格版本。
- **用户反馈与管理。** 达到限额时给出具体类别、已用量和适用时的恢复时间。后台提供依赖健康、队列长度、排队时长、错误率、存储和备份状态。个别模型或天文服务失败时，保留已成功的步骤并提示失败原因。
- **审计和追踪。** 复用 V1.9 运行详情。记录管理员权限、配额变更和任务控制事件，供运维按访问权限核查。日志限制体积及保留期限，使用脱敏状态、计数和关联标识，排除用户正文、文献原文、个人备注和密钥。

## 3. 后台任务可靠性

沿用现有 N 体计算队列、租约、结果记录及隔离绘图能力，统一网页对排队、运行、取消、完成、失败和中断的说明。用户审阅并确认后提交，刷新或关闭网页不影响已接收的任务。回到会话或项目时从服务器读取已保存状态与产物。[现有计算任务运维说明](development/v1.7.0/OPERATIONS.md)

| 场景 | 期望行为 |
| --- | --- |
| 重复提交与并发 | 同一请求只创建一次任务。按账号及全局配额限制认领，使用事务记录尝试和状态 |
| 排队取消与执行取消 | 排队任务直接取消。运行中先标记正在取消，确认进程结束后回收执行槽，迟到的结果无法覆盖取消状态 |
| API 重启与 Worker 故障 | 持久队列保留。能核对仍在运行的任务继续显示，丢失执行状态的任务在核验后标为中断，页面显示处理方式 |
| 超时、失败与重跑 | 分类记录参数、环境、上游与执行错误。用户可确认重跑，产生新尝试和独立证据，保留原失败信息 |
| 产物发布 | 校验文件、大小、来源和完整性后再给出可下载结果。成功记录与产物可对应，已取消或中断任务拒绝发布迟到产物 |

部署手册给出不同主机资源下的起始配置。性能验收记录实际硬件、任务样例、并发和延迟，用于确定受支持容量。

## 4. 备份、恢复与发布验收

1. **备份范围。** 覆盖认证与用户映射、各账号的会话、项目、文献库、RAG 库、计算记录和持久产物。数据库备份与外置产物对应同一个可核对的恢复点。私有配置及必要的加密材料单独受控保存。临时缓存和执行交接目录按各自恢复策略处理。[PostgreSQL 备份与恢复](https://www.postgresql.org/docs/current/backup.html) · [现有 V1.9 运维说明](development/v1.9.0/OPERATIONS.md)
2. **恢复演练。** 在另一个 Compose 项目和独立数据库恢复备份，核对账号归属、核心记录、附件及产物完整性，并用测试账号从浏览器打开恢复的内容。记录备份周期、可恢复时间点和实际耗时。升级失败演练同样核对隔离环境的数据和应用回退。
3. **评估与容量。** 用同一套 V1.9 样例对比升级前后，包括 ADS 检索及入库、SIMBAD→Gaia、RAG 引用、REBOUND／PeTar 和绘图。分别记录科学字段、错误与降级、时延、资源和通过／失败／跳过项。离线样例和真实服务结果分别归档。[V1.9 评估用例](development/v1.9.0/evaluation-cases.json)

**发布验收场景。** 在独立 Linux 环境配置 HTTPS。账号 A 检索并保存文献，账号 B 同时提交 N 体模拟，双方只能访问各自记录。触发一次服务重启，核对文献回执、任务状态、取消或重跑，以及下载权限。将备份恢复到第二套环境，核对账号、文献、数据与计算结果，保留完整证据。

同次验收还应验证额度耗尽只影响对应账号的受限操作，后台的诊断信息足以定位失败，旧链接与归档在更名后仍可使用。发布记录区分启动健康、多人功能、容量和恢复演练各自的通过项与缺口。

## 5. 更名与兼容

产品名称为 **Siderfolio**。网页标题、顶部栏、账号页面、邮件、对话助手与导出说明采用新名称。项目说明保留「原 AstroAgent」以便识别。

按公开展示名与技术标识管理这次升级。`astroagent` Python 包名、`ASTROAGENT_*` 环境变量、Compose 项目和卷标识、数据库架构、API、会话 Cookie 与归档格式沿用既有兼容标识。现有书签、文献来源链接、登录和备份仍按兼容契约工作。仓库地址、域名或包名如需一并更改，按各自的链接、登录和客户端影响单独安排迁移。
